AI 没有消灭工程师，反而让他们更值钱 / AI Made Engineers More Valuable

「AI 取代工程师」是这两年最流行的叙事，今天被两个不同立场的人同时反驳。

中文

Box 的 CEO Aaron Levie 拆掉了「AI 消灭工程师」这套假设：它是这几年最离谱的猜想之一，而且错得离谱。真实发生的是——工程师拿到了一件能加速一切开发的神器。

他的逻辑是：AI 让公司能接的活比以前多得多，所以工程师的价值在很多领域反而上升了。自动化药物研发需要工程师；自动化制造需要工程师；接越来越大的软件项目需要工程师。

今天最锋利的一句话也来自他：模型越来越强，但能被领域里的专家用得更好，而不是新手。「现在是当专家的好时候。」

「工程师会被消灭」是过去最离谱的假设之一，而且错得离谱。我们只是给了工程师一件能加速一切开发的神器。 当然，在那个世界里他们的价值不仅依然关键，在很多领域反而会上升，因为我们可以把工程能力用在比以往多得多的活儿上。 想自动化药物研发，你需要工程师。想自动化制造，你需要工程师。想接越来越大的软件项目，你需要工程师。 这会发生在工程之外的领域。AI 让公司承担的活儿远超从前，也就需要更多专家来监督这些活儿。 即使模型越来越好，它们也能被领域里的专家用得比新手更好。现在是当专家的好时候。

His logic: AI lets companies take on way more work than before, so engineering value goes up in many domains. Automating drug discovery needs engineers. Automating manufacturing needs engineers. Taking on larger and larger software projects needs engineers.

And the sharpest line of the day: even as models get better, they get better utilized by the experts in each field than by novices. 'Great time to be an expert.'

Agent 开始接管日常 / Agents Take Over the Day Job

从「帮你写代码」到「替你维护应用」——agent 正在进入那些没人想干的日常活。

中文

Anthropic 的 Boris Cherny 公布了一个做了几周的实验：让 Claude 接管自家应用的日常维护。一个叫 proj-claude-maintains-apps 的 Slack 频道每天跑一堆例行任务，覆盖 iOS、Android、Desktop、web、CLI 和 Agent SDK——崩溃 fuzzer 在模拟器里乱点找崩溃点并修复；去重器扫描代码库里相似但略有分歧的抽象并统一；死代码清理器删静态不可达的代码；还有专门抓抽象泄漏的「抽象警察」，以及更多。

数字就是故事：几周开出 388 个 PR，其中 180 个经过 Claude Code Review 加人工 review 后合入。「Claude 通常第一把就把 PR 做对了；做不对，我们就让它调自己的 routines，第二天做得更好。」

这是 agent 工作不性感的一面——维护，而不是英雄时刻——而这恰恰是今天最有说服力的信号。

过去几周我一直在做一个奇怪的实验：让 Claude 接管我们应用的日常维护。已经看到早期迹象，这可能是可行的。 设置很简单：我们有一个叫 proj-claude-maintains-apps 的 Slack 频道。Claude Tag 在里面每天跑一堆例行任务，覆盖 iOS、Android、Desktop、web、CLI 和 Agent SDK： - 崩溃 fuzzer：在模拟器里打开应用乱点，找崩溃方式，然后定位根因并修复 - 去重器：扫描代码库里相似但略有分歧的抽象，发 PR 统一它们 - 死代码清理器：删除静态不可达代码，给疑似死代码加日志确认，第二天确认死了就删 - 抽象警察：修抽象泄漏 - 还有一堆别的…… 结果出奇地正面。过去几周，这些例行任务在我们的仓库里开了 388 个 PR，其中 180 个经 Claude Code Review 加人工 review 后合入。我们现在在想怎么简化流程，让这类机械改动更容易合入。 Claude 通常第一把就把 PR 做对了；做不对，我们就让它调 routines，第二天做得更好。有时要调好几天。

English

Results have been surprisingly positive. Over the last few weeks, these routines have opened 388 PRs across our repos, 180 of which we merged after Claude Code Review + human review. We're now thinking about how to streamline this to make merging these kinds of mechanical changes easier. Claude generally gets these PRs right on the first shot, and if it doesn't, we ask Claude to tune its routines so it's better the next day. Sometimes it takes a few days of tuning.

Agent 产品设计：一个大脑还是多个分身 / One Agent or Many?

Grok Bot 发布后，agent 的产品形态之争浮出水面：一个什么都懂的超级 agent，还是一群各管一摊的子 agent？

中文

VC Nikunj Kothari 很喜欢 Grok Bot 的 UX 和 onboarding——然后抛出了真正重要的设计问题：用户想要的是一个握着全部上下文、什么都懂的超级 agent，还是一群各管一摊的子 agent？

他的框架：如果把 agent 当人看，Grok Bot 的设计就说得通——按部门隔离工具、上下文和成果，你有明确目标就去找对应的 bot。如果把 agent 当 Jarvis 看，你想要的是一对一界面背后、能创建并协调所有 bot 的主 agent。

他的判断：长期会收敛到主 agent 当编排者，但起步都会很窄——考虑到上下文窗口、工具调用和成本这些真实约束，他理解大家为什么这么选。

Grok Bot 是个了不起的发布……UX、设计、onboarding 都无可挑剔。 但我一直反复想一个问题：用户（个人和企业）想要的是一个握着全部上下文的超级 agent，还是一群各管一摊的子 agent？ 如果把 agent 当人看，Grok Bot 的设计就完全说得通。它允许我们按部门隔离工具、上下文和成果。你有具体目标，就去找那个 bot。 但如果把 agent 当 Jarvis 看，你想要的是一对一界面背后那个把事情办成的 master agent。它可能会创建并协调完成这个任务所需的所有 bots（甚至包括沟通和上下文）。区别在于界面是 1:1 还是 1:多。 我的猜测是：长期会偏向一个 master agent，它作为编排者，读懂你创建的 bots。但起步都会很窄，就像现在大多数公司做的那样。 P.S. 我理解大家今天选择任务化/单一结果的核心工程约束（上下文窗口、工具调用、简洁性、成本等）。我主要是从设计/产品角度想这个问题。

English

VC Nikunj Kothari loves Grok Bot's UX and onboarding—then asks the design question that actually matters: will users want one super agent that holds all the context, or many sub-agents each doing a slice of tasks?

His framing: if you treat agents like humans, Grok Bot's design makes sense—compartmentalize tools, context and outcomes per division, and you reach out to the bot for the specific goal you have in mind. If you treat agents like Jarvis, you want one master agent that creates and coordinates all the bots behind a 1:1 interface.

His bet: it converges on a master orchestrator over time, but starts narrow—which he understands, given real constraints on context windows, tool use, and cost.

You reach out to that bot for that specific goal that you have in mind. But, if you treat agents as Jarvis, you want a master agent that just gets the job done. It might create and coordinate all the bots (and dare I say the communication/context) that might be needed to do the task. But the interface is 1:1 vs. 1:many. My guess is it'll veer towards the one master agent over time who can then act as an orchestrator who reads / understands the bots you create. But starts narrow as most of the companies are doing it now. PS: I understand the core engineering constraints (context windows, tool use, simplicity, cost etc) why companies are choosing task/singular outcomes today. Primarily thinking this from a design / product side.

中文

这期播客的结论：当机器在棋上超越人类之后，人没有弃棋，反而比任何时候都更在乎它。Chess.com 的 CEO Erik Allebest 讲了一个不太可能的故事：域名来自 2005 年的一场破产拍卖，公司一路 bootstrapped、不靠外部资本，如今拥有 2.5 亿注册会员、约 1000 万日活、年收入 2 亿美元以上，使命是让十亿人下棋。

关于 AI：引擎先让国际象棋变得无聊——Stockfish 下得太完美，棋手们磨出乏味的残局。然后神经网络来了：Leela Chess Zero 下出激进、非传统的棋，把这项运动推向前。「电脑一开始让棋变得有点无聊，后来却让它变得前所未有的精彩。」

他的哲学直击本质：「根本上，人类就是想做人类的事。」AI 没有取代棋手——它让游戏更好玩了，从复盘你棋局的 AI 教练，到按你水平生成的题目。还有他的习惯理论：把你人生中的任何一天乘以一千，大约就是你的一生——每天五道棋题，就是五千道。

还有今年最诚实的一句创始人发言：他们直到 2024 年才意识到国际象棋是一门大生意——那时已经快 20 年了。

我们有超过 2.5 亿注册会员，收入也比我想象中一家国际象棋公司能达到的更多。我想今年会略超 2 亿美元。

根本上，人类就是想做人类的事。就是人和人竞争，就是人类创造东西，就是人类解决问题。

电脑一开始让国际象棋变得有点无聊，但后来却让它变得前所未有的精彩。我们现在看到的棋比任何时候都精彩。

如果你把人生中的任何一天乘以一千，那大概就是你的一生的样子。所以如果你每天做五道棋题，乘以一千，你就做了 5000 道题，你会变强很多。
