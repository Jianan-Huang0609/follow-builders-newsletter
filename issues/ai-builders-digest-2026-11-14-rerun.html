Theme 01

The Loop Is the Product / 闭环本身就是产品

真正的 continual learning 不只是训练一个模型，而是把生产轨迹、评估、训练和部署接成一条能反复运行的产品链。

TD
Training Data
Training Data Podcast
中文

核心结论是：continual learning 只有在训练、eval 和部署处于同一个闭环里时，才真正有用。Trajectory 创始人 Ronak 说，现在的 agent 更像离线地图：能力很强，但路线一变就得整批更新。理想状态是 AI 版 Google Maps，每次真实任务都变成新的 trace，系统持续变好。

实际瓶颈不只是模型架构。团队还需要生产环境里的 trace、可回放的环境，以及把「什么叫好」转成 reward 的方法。Trajectory 把这条链路包装成一键训练和部署；在 Harvey 的案例里，专用模型准确率从约 4% 提升到约 18%，成本却只有 frontier model 的六分之一。

把 training、eval 和 deployment 放在一起，让每个人都能简单使用，然后把模型上传回生产环境，收集新的 traces，形成闭环。

用 Trajectory 训练出的模型便宜六倍，准确率从开源模型的大约 4% 提升到大约 18%。

English

The takeaway: continual learning becomes useful when training, eval, and deployment live in one loop. Trajectory founder Ronak describes today's agents as closer to offline maps: smart, but forced into batch updates whenever the route changes. The target is Google Maps for AI, where every real-world task becomes a new trace and the system keeps improving.

The practical bottleneck is not just model architecture. Teams need production traces, replayable environments, and a way to turn 'what good looks like' into reward. Trajectory packages that path into a one-click train-and-deploy workflow; in the Harvey example, a specialized model moved from roughly 4% to 18% accuracy while costing six times less than a frontier model.

And I think by doing this of of basically putting training, eval, and deployment in one place, making that just dead simple for every single person to do, And then you can close the loop and basically now upload that model back to production, gather new traces.

With Trajectory, what they were able to do is train a model that is six times cheaper, and it goes from around 4% accuracy for an open source model to around 18%.

Theme 02

Measure the Work, Not the Hype / 衡量任务，不要迷信榜单

当模型能力接近时，真正影响工程选择的是 solved task 的成本、可靠性和对具体 workflow 的适配。

GT
Garry Tan
@garrytan
中文

Y Combinator CEO Garry Tan 给出的建议非常具体：Claude Code 里继续把 Opus 5.5 作为默认模型。在 52 个 coding task 的对比中，Fable 5.2 的解决率几乎一样，82.7% 对 84.6%，但每个 solved task 的成本高了 2.8 倍。

这提醒 builder：当一个模型已经能解决大多数普通任务时，真正该看的就不再是 headline score，而是让真实任务成功落地的成本，尤其是难题上的成本。

Claude Code 里把 Opus 5.5 作为 coding 默认模型。52 个 coding task 的测试中，Fable 5.2 解决率差不多（82.7% 对 84.6%），但每个 solved task 的成本高 2.80 倍。

English

Y Combinator CEO Garry Tan's recommendation is unusually concrete: keep Opus 5.5 as the Claude Code default. In a 52-task comparison, Fable 5.2 solved nearly the same share of coding tasks, 82.7% versus 84.6%, but cost 2.8 times more per solved task.

That is a useful reminder for builders: once a model already clears most ordinary tasks, the relevant benchmark is no longer the headline score. It is the cost of getting a real task over the line, especially on the harder cases.

Keep Opus 5.5 as your coding default in Claude Code. On 52 coding tasks in Claude Code 2.1.322, Fable 5.2 solved about as many (82.7% vs 84.6%) but cost 2.80x as much per solved task.

English

Nikunj Kothari pushes back on benchmark-maxxing: there is no substitute for running models on your own workflows. Only a few benchmarks actually matter, and the rest can become marketing hill-climbing that says more about the test than the product.

The editorial point is simple: an eval should answer whether the system works for the job you need, not whether it can win a leaderboard built around somebody else's job.

There’s no substitute to really using the models for your workflows to understand the best ones that actually work for your workflows.
