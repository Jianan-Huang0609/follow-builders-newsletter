Theme 01

Evals Are the Product / Evals 就是产品规格

当 agent 要进入真实工作流，评测不再是上线前的 QA，而是决定产品该做成什么样的规格。

中文

Meta AI Director Madhu Guru 指出团队做 agent 时最常见的错误：等产品做完，才把 eval 当成额外的 QA 步骤。他更锋利的判断是，AI 产品从根上就不同，所以 eval 套件应该一开始就定义产品到底要做到什么。

顺序应该反过来：先写清楚成功的证据，再去打磨 demo。

团队最常见的错误，是等 agent 做完后才把 eval 当作额外的 QA。 AI 产品从根本上不同。 你的 eval 就是产品规格。

English

Meta AI director Madhu Guru names the most common mistake teams make with agents: treating evals as a QA step after the product is built. His sharper framing is that AI products are different at the foundation, so the eval suite should define what the product is supposed to do in the first place.

That is a useful change in sequence: write the evidence of success before polishing the demo.

The most common mistake teams make is to treat evals as an additional QA step once the agent is built. AI products are fundamentally different. Your evals are your product spec.

Theme 02

Hard Constraints for Agents / 给 Agent 加硬约束

当代码主要由 agent 生成时，编译器、类型系统和结构化规划会变成新的协作边界。

中文

Vercel CEO Guillermo Rauch 发布了 gdp-ts：一个围绕编译期 authorization proof 设计的 TypeScript library、linter 和 AI skill。敏感函数要求调用方已经完成正确的 role 与 entitlement 检查，typechecker 会在代码发布前验证这份契约。

更大的想法是，agent 反而很适合人类觉得麻烦的硬约束。既然 agent 写出的代码已经多到团队审不完，正确性就需要直接进入工具链。

介绍 gdp-ts：Ghosts of Departed Proofs for TypeScript。 gdp-ts 是一个用于更安全 API 设计的 library、linter 和 AI skill。在这个契约下，敏感函数要求调用方提供已经完成 authorization check 的“proof”。 typechecker 会在编译期验证这些 proof，防止团队和 agent 发布灾难性的安全漏洞以及其他 bug。 这些模式其实存在很久了，尤其在 Haskell 等生态里，但人工 code review 以及认知和语法负担让它们一直很小众。 现在情况反过来了。Agent 写出的代码比我们能审查的更多，而它们特别适合在会让人类烦躁的严格约束循环里工作。Rust、borrow checker 以及代码美学争论的兴起都说明了这一点。 README 和示例模拟了一个真实的 Vercel API 约束：修改 Project 密码，需要特定 role 和 entitlement 的 proof。感谢 Matt Noonan 和 Ollie Charles 在这一领域的研究。 https://t.co/eRWdiMvQ2V

English

Vercel CEO Guillermo Rauch introduces gdp-ts, a TypeScript library, linter, and AI skill built around compile-time authorization proofs. Sensitive functions require evidence that the caller has already passed the right role and entitlement checks, and the typechecker verifies that contract before code ships.

The larger idea is that agents benefit from constraints humans often find tedious. As agents write more code than teams can review, correctness needs to move into the tooling itself.

Introducing gdp-ts: Ghosts of Departed Proofs for TypeScript. gdp-ts is a library, linter and AI skill for safer API design. Under this contract, sensitive functions require 'proofs' that the caller performed an authorization check. The typechecker verifies these proofs at compile time, preventing your team and agents from shipping catastrophic security (and other kinds of) bugs. While these patterns have existed for quite some time, especially in ecosystems like Haskell, ① human code review and ② cognitive and syntactic overhead made these solutions niche. The situation is now inverted. Agents are writing more code than we can review, and they *thrive* in tight loops with hard constraints that would frustrate us. We see this with the rise of Rust, borrow checker, code aesthetics debate and all. The README and examples model a real-world Vercel API product constraint: changing the password on a Project requires a proof of a certain role + a certain entitlement. Thanks to Matt Noonan and Ollie Charles for their research in this space. https://t.co/eRWdiMvQ2V
