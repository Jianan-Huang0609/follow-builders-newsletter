Theme 02

Long-Horizon Agents / 长时程 Agent 的工程哲学

当目标从写代码变成做税表，验证方式彻底变了——Basis 的答案是：过程重于结果，把人类流程写成 behavior spec。

MT
Mitch Troyanovsky (Basis)
The MAD Podcast with Matt Turck
中文

Basis 的联合创始人 Mitch Troyanovsky 在给真实经济做长时程自主 agent——做税表，而不是写代码。他的核心论点：过程重于结果。税表没法「编译」，你不能只奖励最终数字；你得把「工作应该怎么做」写进一份 markdown 的 behavior spec（行为规范），它同时兼任给 agent 轨迹打分的评分标准。会计和 ML 研究员一起写这些 spec，而裁判本身也是一个 agent，要读完整条轨迹。

为什么编程成了第一个成功的 agent 用例？因为它在运行时就可验证、便宜、而且是纯文本——「就算你是世界上最牛的工程师，总会在某处犯个语法错误。」还有一个被人忽略的因素：实验室里全是工程师，他们保证了训练数据的高质量，所以 agent 学到的不仅是跑通测试，还有工程品味。

他最锐利的重新定义：context 就是运行时训练数据，prompt 里的英文比代码更珍贵。「英文更珍贵，因为英文影响性能，代码不影响性能。」而在真实经济里你不需要 Move 37，你需要的是能规模化到一家公司的工作。关于护城河：他完全预期 harness 工程会被模型吞掉——五年以内，而不是两年以内。在那之前，「技术护城河不是真正的护城河」，重要的是商业位置和工作流所有权。Basis 正和 Brain Trust 一起把 behavior spec 开源，想把它做成行业标准。

有太多方式可以「通过」所谓的结果，却没有正确执行过程。人类早就习惯了和非确定性系统一起工作——只不过这些系统通常是同事，而不是电脑。

就算你是世界上最好的工程师，总会在某个地方写出一个语法错误。所以编程在运行时那么容易验证，这件事本身就极有价值，而且验证成本很低。

英文更珍贵，因为英文影响性能，代码不影响性能。技术护城河不是真正的护城河……我完全预期它会被吞掉，我一点也不担心，那绝对是未来。大概五年以内，我不觉得是两年以内。

English

Mitch Troyanovsky, co-founder of Basis, is building long-horizon autonomous agents for the real economy, tax returns rather than code. His core thesis: process beats outcomes. A tax return can't 'compile', so you can't just reward the final number; you encode how the work should be done in a markdown 'behavior spec' that doubles as a rubric for grading the agent's trajectory. Accountants and ML researchers write them together, and the judge is itself an agent that reads the whole trajectory.

Why did coding become the first successful agent use case? Because it's verifiable at runtime, cheap, and text-based: 'even if you were the best engineer in the world, you're gonna have a syntax error at some point.' Plus a factor people miss: labs full of engineers made sure training data was high quality, so agents are learning engineering taste, not just test-passing.

His sharpest reframe: context is runtime training data, and the English matters more than the code. 'The English is more precious because the English affects the performance, the code does not affect the performance.' And in the real economy you don't want Move 37s, you want work you can scale to a company. On moats: he fully expects harness engineering to get swallowed by the model, within five years rather than two. Until then, 'technical moats are not real moats'; what matters is business position and workflow ownership. Basis is open-sourcing its behavior specs with Brain Trust to seed an industry standard.

There are lots of ways to pass quote unquote outcomes without, you know, having done the process properly. Humans are already used to working with non-deterministic systems — it's just the systems are normally their co-workers, not their computers.

Even if you were the best engineer in the world, you're gonna have a syntax error in which the thing is wrong at some point. And so the fact that coding is so easily verifiable at runtime is obviously very valuable, and it's cheap to do.

The English is more precious because the English affects the performance, the code does not affect the performance. Technical moats are not real moats... I assume it will be swallowed up. Yeah, I'm not worried about it. That is absolutely the future. It's probably sub five years. I don't think it's sub two years.

The Economics of Cheap Intelligence / 智能变便宜之后的经济学

成本崩塌不会让需求消失，而是让以前不划算的用例变得可行——企业形态也跟着在变。

中文

Madhu Guru 把一条经典的需求侧经济学推到 AI 上：蒸汽机效率越高，煤炭需求越大；高级语言让编程更容易，结果软件被造出了远多于从前；电子表格让财务分析变便宜，企业就做了远多于从前的分析。当一个任务的成本和复杂度下降，新的用例在经济上就变得可行了。

他的预测：AI + 软件工程会走同样的路——远多于此前的软件，去解决远多于此前的问题，包括那些以前在经济上根本不可行的。对 builder 来说，这个反直觉的结论是：更便宜的智能不是需求的杀手，而是需求的引擎。

蒸汽机效率提升增加了煤炭需求。高级语言让编程更简单，结果造出了多得多的软件。电子表格让财务分析更便宜，企业就做了多得多的分析。当一个任务的成本和复杂度下降，新用例就变得经济可行。AI + 软件工程很可能遵循同样的模式：多得多的软件解决多得多的难题，包括以前经济上不可行的问题。

English

Madhu Guru runs the classic demand-side argument forward for AI: more efficient steam engines increased coal demand; higher-level languages produced far more software; spreadsheets made financial analysis cheaper and businesses did far more of it. When the cost and complexity of a task falls, new use cases become economically viable.

His prediction: AI plus software engineering follows the same pattern, far more software solving far more problems, including ones that were previously economically unviable. For builders the counterintuitive takeaway is that cheaper intelligence isn't a demand killer, it's a demand engine.

Making steam engines more efficient increased coal demand. Higher-level languages made programming easier and resulted in far more software being built. Spreadsheets made financial analysis cheaper and resulted in businesses doing far more analysis. When the cost and complexity of a task falls, new use cases become economically viable. AI + software engineering will likely follow the same pattern: far more software solving far more problems, including problems that were previously economically unviable.

Platforms Fight Back / 平台开始反制

X 用行为模型对付 AI slop，但算法不读内容——高级内容工厂还留着一个大漏洞。

中文

Peter Yang 好奇 X 是怎么对抗 AI slop 的，于是去翻了它的开源算法。答案是一个叫 TweetSpamBot 的行为模型：分析账号最近最多 512 个动作，看发帖爆发、引用转推行为、时间节奏、两次动作之间的浏览/停留等信号，专门识别 TWEET_CREATE_BURST、QUOTE_TWEET_SPAMMER、CONTENT_AMPLIFIER 这类模式。

他的发现：高分可以触发账号挑战，但似乎并不会给 slop 帖子本身降权——而且这个模型根本不读帖子内容。所以一个老练的 AI 内容工厂照样能全天候发 slop：找爆款、用同一套模板引用转推（钩子→数字→背景故事→结论）、每天跨领域重复 10 次以上。「现在的护栏太容易绕过了。」

我好奇 X 如何对抗 AI slop，所以去看了它的开源算法。它有一个叫 TweetSpamBot 的行为模型，分析账号最近最多 512 个动作，关注发帖爆发、引用转推行为、时间节奏、以及动作之间的正常浏览或停留等信号。

模型被训练来识别这样的模式：TWEET_CREATE_BURST / QUOTE_TWEET_SPAMMER / CONTENT_AMPLIFIER。高分可以触发账号挑战，但似乎不会给 slop 帖子本身降权。我认为缺口在于模型不读实际的帖子内容。所以一个老练的 AI 内容工厂依然可以整天发 slop：1.找爆款 2.每次用同一模板引用转推：钩子→数字→背景故事→结论 3.每天跨不相关主题重复 10 次以上。现在的护栏太容易绕过了。

English

Peter Yang dug into X's open-source algorithm to see how it fights AI slop.
