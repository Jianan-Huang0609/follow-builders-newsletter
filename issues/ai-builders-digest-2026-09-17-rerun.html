Theme 01

One Claude, Many Outputs / 一个 Claude，多种产出

产品边界正在从“你该打开哪个 App”转向“你想完成什么任务”。这会把路由复杂度从用户手里移到 agent 身上。

中文

Claude Code 证明了 AI 不只是会回答问题，也能接过一个功能 brief，最后交付可用的代码。Boris Cherny 说，Cowork 把同样的模式带到了知识工作，而下一步是把两者合并成一个能跨任务保留上下文的 Claude。

真正重要的不是产品合并本身，而是把“我该用哪个入口”这个负担从用户手里拿走。用户只需描述目标，Claude 再判断该快速回答、深度执行，还是直接交付文件，同时用户仍能随时停止或改道。

Claude Code 证明了 AI 可以做真实工作，而不只是回答问题。开发者把一个功能交给 Claude，回来时代码已经交付。 Cowork 证明知识工作者也可以这样做：把 brief 交给 Claude，回来时文件已经完成。 今天，chat 和 Cowork 开始合并成一个 Claude。方向是：无论你在哪里工作，都由一个 Claude 跨越你正在处理的一切并携带上下文。

English

Claude Code proved that AI could take a feature brief and return shipped code. Boris Cherny says Cowork extended that idea to knowledge work, and the next step is merging both into one Claude that carries context across the things you are working on.

The important product decision is not the merger itself, but removing the routing burden from the user. One prompt can now lead to a quick answer, deeper agentic work, or a finished file, while the user can still stop or redirect the process.

Claude Code showed that AI could do real work, not just answer questions. Developers hand Claude a feature, come back to shipped code. That's where much of the industry's serious engineering runs now. Cowork proved knowledge workers could do the same: hand Claude the brief, come back to finished files. Today, chat and Cowork start merging into one Claude. The direction: one Claude that carries context across everything you're working on, wherever you are. Simple enough for everyone to access Claude's full capabilities.

Theme 02

Tools That Fit the Agent / 给 agent 合适的工具

agent 的可靠性不只取决于模型聪不聪明，也取决于你给它的工具是否贴近真实任务。

T
Thariq
@trq212
中文

Thariq 认为，工具设计正在走出“什么都暴露成 bash”的旧习惯。如果 agent 要存数据，给它一个像 database 一样的 API，可能比让它操作 filesystem 更可靠；但涉及代码生成和执行时，sandbox 加 bash 依然很合适。

关键不是简单站队“要不要 bash”，而是让接口匹配任务本身，不要逼模型绕一层间接层。

我觉得越来越多时候，你可以直接给 Claude 提供形状符合你需求的工具，而不是用一层间接层去欺骗它。比如做数据存储时，你真的想要 filesystem，还是想要一个 database API？这也是我相比去年更新后的看法。

English

Thariq argues that tool design is moving past the old habit of exposing everything as bash. If an agent needs to store data, an API shaped like a database may be more reliable than asking it to manipulate a filesystem; sandboxes and bash still make sense when the task is code generation and execution.

The useful distinction is not 'bash versus no bash'. It is matching the interface to the job instead of forcing the model through an indirect layer.

I think increasingly you can just give Claude tools shaped in the way you want vs tricking it with a layer of indirection e.g. for data storage do you really want a file system or do you want an API to a database this is again, an update to me from last year

Context, Safety & Ownership / 上下文、安全与归属

当 agent 开始进入真实工作流，谁能读取什么、如何限制风险、上下文归谁所有，都会变成产品核心。

中文

Nikunj Kothari 花了几个月做一个家庭 agent，真正有意思的是它的颗粒度：这是一个两个人共同使用的 bot，但可以只读取指定邮件、把邮件内附件转成结构化数据，还能在登录状态的浏览器 session 里工作。他说，通用 bot 很难复现这种控制力。

这里的启发是：personal agent 的价值来自边界和长期积累的上下文，不只是更大的模型。

我花了几个月折腾 @NousResearch 的“Home” agent，它终于变得很好用了。它也是我们第一个“群组” bot，我和妻子每天都会和它互动，尤其是它失败的时候，学习过程很有意思。😅 我试过用 Grok Bot 之类的重做，但做不到这么细的颗粒度和控制力，比如只读取某些邮件、把行内附件转成结构化数据，或使用登录状态的浏览器 session。

English

Nikunj Kothari has been building a household agent for months, and the interesting part is its granularity: a shared bot for two people that can read only selected emails, turn inline attachments into structured data, and work through logged-in browser sessions. He says this level of control is hard to reproduce with a generic bot.

The lesson is that personal agents become useful through boundaries and accumulated context, not just a bigger model.

I have tried to recreate with Grok Bot and similar and you can’t get this level of granularity and control (eg only read certain emails, convert in line attachments to structured data or logged in browser sessions)
