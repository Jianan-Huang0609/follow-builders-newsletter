Theme 01

Agent Scale Hits GitHub / Agent 规模冲到 GitHub

当 agent 开始批量写代码，平台问题就不再是“会不会生成”，而是 review、merge、权限、成本和维护者控制权。

KD
Kyle Daigle
GitHub COO on AI & I by Every
中文

GitHub COO Kyle Daigle 从平台层给了一个非常清楚的 agent economy 截面：仅 3 月，就有 1700 万个 PR 是由 agent 创建的；如果按线性增长估算，GitHub 今年会走向 140 亿次 commit。

他的重点不是说这些代码全是 slop。更大的变化是，开发者正在和一个、两个甚至一组 agent 一起工作，这些 agent 会使用他们的技能、上下文和资源。于是问题变得很现实：怎么帮维护者处理 PR 洪水，同时又不替每个开源社区做决定？

GitHub 的答案是先做 building blocks：agentic code review、agentic merge、等待 CI 和 policy 的自动化，以及维护者控制谁能贡献、贡献前需要证明什么。最值得注意的是克制：GitHub 想给工具，但不急着替开源世界规定唯一标准。

3 月有 1700 万个 PR 是 agent 创建的，而且这只是 agent PR。

如果增长是线性的，今年会走向 140 亿次 commit，当然实际不会只是线性。

我们现在专注于给维护者提供控制权的 building blocks。等大家一起学习、维护者反馈进来，如果某个完整系统自然浮现，我们再把它固化。

English

GitHub COO Kyle Daigle gives one of the clearest snapshots of the agent economy from the platform layer: in March alone, 17 million pull requests were created by agents, and GitHub is on track for 14 billion commits this year if growth were linear.

His point is not that all this code is slop. The bigger shift is that developers are starting to work with one, two, or many agents that use their skills, context, and resources. That creates a very practical infrastructure problem: how do you help maintainers handle the flood without taking control away from each community?

GitHub's answer is building blocks: agentic code review, agentic merge, policy-aware automation, and maintainer controls over who can contribute and under what conditions. The interesting part is the restraint: GitHub wants to provide tools, but not prematurely declare one universal standard for open source.

In March, you know, there were 17,000,000 pull requests that were created by agents. Yeah. That's just the agent pull requests.

We're on track to be 14,000,000,000 if the growth is linear this year, which it would not be.

We're focusing on the the building blocks of controls for maintainers. And then as we all are kinda learning together and as maintainers send feedback in, we'll, you know, we'll cement an entire system if one emerges.

Theme 02

The Applied AI Moat / 应用层的真实护城河

企业 AI 的价值开始从“接上模型”转向“把模型嵌进复杂工作”。这也是薄应用和深工作流的分水岭。

中文

Box CEO Aaron Levie 系统梳理了 applied AI layer 在规模化时的打法。他对“薄薄套一层 LLM”的反驳很直接：在企业里真正跑通 agentic workflow，复杂度远高于给 LLM 加一个聊天框。

他列出的组件才是护城河：面向 workflow 的功能、上下文采集、专用工具、human-in-the-loop UX、在 frontier model 和便宜模型之间做 model routing、具体任务的 eval、FDE 式实施、change management，以及行业化 GTM。

最该记住的一句是：即使模型能力继续进步，企业今天也需要人帮它们改变。这种帮助不是临时麻烦，而是 applied AI 公司积累价值的地方。

虽然一开始有人批评这只是 LLM 上很薄的一层，但事实证明，在企业里推动 agentic workflow 要复杂得多。

应用层需要扮演 model router，在 frontier intelligence 和更便宜的模型之间做平衡。

也许最终 bitter lesson 会解决很多事，但企业今天就需要帮助来改变。

English

Box CEO Aaron Levie lays out a serious playbook for the applied AI layer at scale. His pushback against the 'thin wrapper' critique is simple: driving agentic workflows inside enterprises is far more complex than putting a chat box on top of an LLM.

The components he names are the actual moat: workflow-specific features, context capture, bespoke tools, human-in-the-loop UX, model routing between frontier and cheaper models, deep task evals, FDE-style implementation, change management, and domain-specific GTM.

The line to remember: even if model intelligence keeps improving, enterprises need help changing today. That help is not a temporary inconvenience. It is where applied AI companies can accumulate value.

Despite some of the initial critique that this would just be a thin layer on the LLM, it’s turning out that actually driving agentic workflows in an enterprise is far more complex.

Act as the model router balancing frontier intelligence with cheaper models.

A final note. There remains a view that a lot of this is all mitigated by model intelligence alone, and the bitter lesson solves all of this in the limit. That’s possibly true, but enterprises need help changing today.

Theme 03

Cost, Routing, and Personal Context / 成本、路由与个人上下文

下一代 AI 工具的关键体验，可能不是更会聊天，而是知道什么时候该用贵模型、什么时候该省钱，以及怎样像懂你一样工作。

KD
Kyle Daigle
GitHub COO on AI & I by Every
中文

Kyle Daigle 对“200 美元订阅变 2000 美元账单”这个问题的最实用答案，是 model routing。开发者的思路会在难题和简单收尾之间来回切换，但几乎没人会为了最后一个命名清理，手动从昂贵 frontier model 切到便宜模型。

他的判断是，工具应该理解 task intent 并自动路由，同时让用户设置质量阈值：这个问题很难，值得用最强模型；这个只是小修改，可以便宜跑。AI 从玩具变成可控成本的生产系统，差别就在这里。

他还把同一件事延伸到 personalization：长期的好体验，是 agent 像在替你补完一个想法，而不是逼你把所有偏好都手写成规则。

我认为关键会是，尤其对开发者来说，工具怎么帮你自动选择模型。

比如带 task intent 的 auto model router。Microsoft Foundry 也有 model router，可以在 API 层做这件事。

真正好的体验，是 agent 像在替你补完一个想法，尤其是当你不需要亲手把这个想法 codify 给 agent 时。

English

Kyle Daigle's most practical answer to the '$200 subscription becomes $2,000' problem is model routing. Developers drift in and out of hard and simple problems, but almost nobody manually switches from an expensive frontier model to a cheap model for the last naming cleanup.

His view is that tools should infer task intent and route automatically, while letting the user set quality bars: this is very hard and worth going to the top, or this is small and can run cheaper. That is the difference between AI as a toy and AI as a cost-controlled production system.

He connects the same idea to personalization: the long-term great experience is an agent that feels like it is completing a thought for you, without forcing you to codify every preference by hand.

I also think it's really, really gonna be about how can we, particularly for developers, help you automatically choose the models.

Like the auto model router with task intent and GitHub. Microsoft Foundry has a model router as well that can do this, use sort of at an API level.

Using an agent that you feel like is completing a thought for you, will give you that great experience, especially if you did not have to personally codify that thought to your agent.

Taste Before Automation / 自动化之前先有品味

越是 AI 能快速生成，越需要人先知道什么是好东西、真实用户会不会用，以及哪些词其实在讨论不同问题。

中文

Zara Zhang 给出了今天最清楚的写作建议：在形成自己的 taste 和 voice 之前，不要用 AI 写作。危险不在于 AI 写作天然不好，而在于如果你不知道什么是好内容，AI 写出 slop 时你也认不出来。

她的解法很传统，但很对：多读，知道好东西长什么样；多写，知道自己的声音是什么；然后再用 AI 放大自己。AI 可以帮你写，但最后还是要像你。

在形成自己的 taste 和 voice 之前，不要用 AI 写作。

用 AI 写作本身不是坏事。危险在于你还没形成对好内容的判断力就开始用 AI 写，如果 AI 产出 slop，你甚至认不出来。

多读，搞清楚好内容长什么样。多写，知道自己的声音是什么。然后再用 AI 帮你写，但要确保它听起来像你。

English

Zara Zhang gives the cleanest writing advice of the day: don't use AI for writing until you have developed your own taste and voice. The danger is not that AI writing is inherently bad, but that if you do not know what good looks like, you will not recognize slop when it appears.

Her prescription is old-fashioned in the best way: read a lot, write a lot, then use AI as leverage. AI can help you write, but it should still sound like you.

Using AI to write isn't inherently bad. The danger is using AI to write before you've developed your taste for what is good content. If the AI produces slop, you won't even recognize it as slop

Read a lot to figure out what good looks like. Write a lot to know what your voice sounds like. Only then, use AI to help you write, but make sure it actually sounds like you
